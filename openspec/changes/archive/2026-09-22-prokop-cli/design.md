## Context

`prokop` — ядро агента: цикл хода (`loop`), инструменты (`tools`), навыки
(`skills`), память (`memory`), хранилище сессий (`store`), провайдеры
(`providers`), планировщик (`cron`), делегирование (`subagents`), терминальные
бэкенды (`backends`), гейтвей (`gateway`), GUI (`computer`). Все модули
специфицированы в `openspec/specs` и покрыты тестами (221).

Чего нет — **точки входа**. Сегодня ядро запускается двумя способами: из
Python-кода или как MCP-сервер для opencode (`~/.config/opencode/mcp-servers/prokop_mcp.py`,
вне репозитория). Самостоятельно из терминала `prokop` не запускается: в
`pyproject.toml` нет `[project.scripts]`. У аналога (Hermes Agent) есть CLI и
TUI — это гэп P1 в `docs/PARITY.md`.

Ограничения:
- минимализм зависимостей: `httpx`, `PyYAML` и всё (CLI-фреймворк добавлять
  не хочется);
- платформенная нейтральность: раскладка состояния — `~/.prokop/<профиль>`
  (`PROKOP_HOME`), никаких личных путей (инварианты `docs/PLATFORM_NOTES.md`);
- консоль Windows по умолчанию не UTF-8;
- тесты не должны ходить в сеть (CI без ключей).

## Goals / Non-Goals

**Goals:**
- `prokop` как исполняемая команда после `pip install` — на Windows, macOS и Linux.
- Ядро самодостаточно: ход агента, сессии, планировщик, навыки, провайдеры,
  конфигурация и диагностика окружения — из терминала.
- Ноль дублирования логики: команды вызывают существующие модули ядра.
- Предсказуемый машинный интерфейс: `--json` и коды возврата для скриптов.
- Тесты CLI работают без сети и без ключей модели.

**Non-Goals:**
- TUI/полноэкранный интерфейс — отдельный, больший гэп; здесь только линейный
  REPL.
- Веб-дашборд и API-сервер (отдельные гэпы `docs/PARITY.md`).
- Плагины, hooks, темы/скины.
- Изменение поведения ядра: CLI не добавляет новых требований к `loop`,
  `cron`, `store` и прочим — только вызывает их.
- Управление сервисом (демон/автозапуск) — вне скоупа.

## Decisions

### D1: `argparse` из стандартной библиотеки, без CLI-фреймворка
Подкоманды через `add_subparsers`. Альтернативы (`click`, `typer`) отвергнуты:
новая зависимость ради сахара, а требование проекта — минимум зависимостей и
предсказуемая установка в контейнере.

- *Рационально*: нулевая стоимость установки, нет рисков несовместимости,
  справка и коды ошибок из коробки.

### D2: CLI — тонкий диспетчер над ядром
Каждая команда — небольшая функция, которая собирает зависимости из ядра
(`ProviderRegistry`, `AgentTurn`, `SessionStore`, `JobStore`/`Ticker`,
`SkillIndex`, `load_config`) и печатает результат. Логика хода, хранения,
расписаний не дублируется.

- *Рационально*: одно место правды; поведение CLI автоматически следует за
  ядром и его спеками.

### D3: Явное разделение «локальных» и «сетевых» команд
`sessions`, `skills`, `providers`, `config`, `doctor`, `cron` работают без
ключа модели. Сеть нужна только `turn` и `chat`.

- *Рационально*: диагностика и инспекция доступны всегда, в том числе в CI и
  на чистой установке; понятная ошибка вместо падения при отсутствии ключа.

### D4: Два формата вывода — текст по умолчанию, `--json` для скриптов
Текстовый режим — человекочитаемый и краткий; `--json` — стабильная схема
(`ensure_ascii=False`, UTF-8).

- *Рационально*: один инструмент и для человека, и для автоматизации
  (например, из планировщика ОС или из другого агента).

### D5: Коды возврата фиксированы
`0` — успех; `1` — ошибка пользователя или конфигурации (нет ключа, нет
профиля, неверные аргументы); `2` — ошибка исполнения (модель/инфраструктура).
Разбор аргументов при ошибке тоже даёт `1`, а не `2` (argparse по умолчанию
использует `2` — переопределяется).

- *Рационально*: скрипты и cron различают «я сделал не то» и «оно сломалось».

### D6: Кроссплатформенный stdio — отдельная функция настройки
Перед выводом CLI приводит потоки к UTF-8 (`reconfigure(encoding="utf-8")`),
где это поддерживается; на остальных платформах — no-op. Кириллица и пробелы
в путях передаются как аргументы, без склейки в командную строку.

- *Рационально*: снимает класс ошибок `UnicodeEncodeError` на Windows, не
  ломая POSIX.

### D7: Тестируемость через инъекцию зависимостей
`main(argv, deps=None)`: при `deps=None` собираются настоящие зависимости, в
тестах передаётся объект с фейками (фейковый транспорт модели, временный
`PROKOP_HOME`). Сеть и ключи не нужны.

- *Рационально*: CLI покрывается юнит-тестами так же, как остальное ядро.

### D8: `chat` — линейный REPL, а не TUI
Цикл «прочитал строку → ход → вывел ответ»; выход по `exit`/`quit`/EOF
(`Ctrl-D`/`Ctrl-Z`). Без полноэкранной отрисовки, панелей и истории стрелками.

- *Рационально*: TUI — отдельный гэп со своим изменением; линейный REPL уже
  закрывает сценарий «поговорить с агентом из терминала» и не тянет
  зависимостей.

## Risks / Trade-offs

- [Расхождение CLI и ядра при будущих правках] → CLI не содержит логики; тесты
  CLI проверяют диспетчеризацию и формат, поведение — на тестах ядра.
- [Кодировка консоли на Windows] → явная настройка stdio (D6) + тест на
  кириллицу в выводе.
- [`chat` в неинтерактивном окружении (нет TTY) и в CI] → при отсутствии TTY
  `chat` читает stdin до EOF и завершается с кодом `0`; это же покрыто тестом.
- [Ломающее изменение кодов возврата argparse] → переопределение на `1`
  задокументировано в спеке и закреплено тестом.
- [Разрастание CLI до второго продукта] → Non-Goals и скоуп MVP в tasks;
  расширения — отдельными изменениями OpenSpec.
- [Профиль по умолчанию пишется в домашний каталог пользователя] → путь
  переопределяется `PROKOP_HOME`; в тестах всегда временный каталог.

## Migration Plan

1. Добавить пакет `cli` и `[project.scripts]` — существующее поведение ядра не
   меняется, регресса нет.
2. Переустановить пакет (`pip install -e src`) — команда `prokop` появляется.
3. Прогнать тесты CLI в матрице CI (ubuntu/windows/macos).
4. Обновить README/GUIDE/PARITY.

Откат: удалить `src/prokop/cli/` и секцию `[project.scripts]` — ядро и его
потребители (MCP-сервер, оркестратор) не затрагиваются.
