## Context

Ядро исполняет команды (`backends`) и умеет править файлы, но механизма
отката нет. Любая автономная работа (особенно с авто-одобрением) может
испортить рабочее дерево, и вернуть прежнее состояние нечем. У аналога
(Hermes Agent) есть checkpoints и rollback — гэп P1 в `docs/PARITY.md`.

Ограничения:
- платформенная нейтральность: никаких теней ФС, симлинков (на Windows требуют
  прав) и ОС-специфичных снапшотов — только копирование файлов;
- минимум зависимостей: стандартная библиотека;
- хранилище — в домашнем каталоге профиля (`prokop.home`), не в проекте;
- откат не должен быть необратимым;
- объём не должен расти бесконечно.

## Goals / Non-Goals

**Goals:**
- Снимок набора путей (файлы и каталоги) с манифестом и содержимым.
- Список снимков и восстановление из выбранного.
- Страховочный снимок перед восстановлением (откат отката).
- Разумные пределы: потолок числа снимков, потолок размера отдельного файла,
  правила игнорирования.
- Безопасное поведение по умолчанию: лишние файлы не удаляются.
- Доступность и человеку (CLI), и агенту (инструмент).

**Non-Goals:**
- Снапшоты всей файловой системы и инкрементальные цепочки дельт.
- Хранение истории git и интеграция с ней.
- Откат состояния вне файлов (базы, внешние сервисы).
- Автоматический снимок перед каждой командой (дорого и непредсказуемо).
- Шифрование хранилища.

## Decisions

### D1: Копирование файлов вместо теней ФС и симлинков
Содержимое сохраняется блобами в каталоге снимка.

- *Рационально*: работает одинаково на Windows/macOS/Linux; симлинки на Windows
  требуют прав (в `docs/PLATFORM_NOTES.md` это уже отмечено как источник
  платформенных различий), тени ФС — тем более.
- *Альтернатива* (жёсткие ссылки): ломаются при правке файла «на месте» —
  снимок менялся бы вместе с оригиналом.

### D2: Манифест снимка как источник истины
`<профиль>/checkpoints/<id>/manifest.json` перечисляет записи: абсолютный путь,
вид (файл/каталог), имя блоба, размер. Индекс всех снимков — `index.json`
рядом, перезаписывается атомарно.

- *Рационально*: восстановление не зависит от текущего состояния ФС; индекс
  даёт быстрый список без чтения манифестов.
- *Альтернатива* (обходить дерево снимка): не восстановить пути, которые
  исчезли.

### D3: Лишние файлы по умолчанию не удаляются
`restore` возвращает содержимое файлов и воссоздаёт отсутствующие; удаление
файлов, появившихся после снимка, выполняется только по явному флагу
`--remove-extra`.

- *Рационально*: откат не должен уничтожать данные, которых в снимке не было
  (например, чужую работу в том же каталоге). Разрушительная часть — только по
  явному запросу.
- *Альтернатива* (полное приведение дерева к снимку): необратимо и опасно по
  умолчанию.

### D4: Страховочный снимок перед восстановлением
`restore` сначала создаёт снимок текущего состояния с меткой о причине.

- *Рационально*: сам откат становится обратимым — цена нескольких копий
  несопоставима с потерей данных.
- *Альтернатива* (без страховки): ошибка отката необратима.

### D5: Правила игнорирования и потолки
По умолчанию игнорируются служебные каталоги и файлы (`.git`, `node_modules`,
`__pycache__`, `*.pyc`, `.venv`, `.pytest_cache`, `*.egg-info`), файлы больше
потолка не копируются (запись помечается пропущенной), число снимков
ограничено (старые удаляются).

- *Рационально*: хранилище остаётся обозримым; без потолков один снимок
  каталога с зависимостями съел бы диск.
- *Альтернатива* (без игнорирования): снимок `node_modules` бесполезен и
  огромен.

### D6: Идентификаторы снимков — время + случайность
`<YYYYMMDD-HHMMSS>-<hex>`: сортируется по времени и не конфликтует при
быстром создании подряд.

- *Рационально*: читаемость в списке и отсутствие коллизий.

### D7: Инструмент агента — отдельный набор `checkpoints`
Инструмент `checkpoint` (`create`/`list`/`restore`/`prune`) регистрируется в
наборе `checkpoints`, который включается явно.

- *Рационально*: возможность доступна агенту, но не навязывается: набор
  включается в конфигурации профиля, как `gui` и `mcp`.
- *Альтернатива* (всегда включён): расширяет поверхность инструментов без
  согласия пользователя.

## Risks / Trade-offs

- [Рост хранилища] → потолок числа снимков + потолок размера файла +
  `prune`; старые снимки удаляются автоматически при превышении.
- [Откат уничтожит чужие данные] → D3: по умолчанию ничего не удаляется.
- [Ошибка отката необратима] → D4: страховочный снимок перед восстановлением.
- [Снимок незавершён из-за ошибки чтения] → проблемные пути пропускаются и
  перечисляются в отчёте, снимок остаётся валидным для остальных.
- [Кириллица и пробелы в путях] → пути хранятся строками в UTF-8, содержимое
  копируется байтами.
- [Секреты попадают в снимок] → снимки лежат в домашнем каталоге профиля, а не
  в проекте; правила игнорирования настраиваются пользователем.

## Migration Plan

1. Добавить пакет `checkpoints` и секцию конфигурации — существующее поведение
   не меняется (без снимков ничего не создаётся).
2. Добавить набор `checkpoints` и подкоманду CLI.
3. Обновить документацию и `docs/PARITY.md`.
4. Прогнать тесты в матрице ubuntu/windows/macos.

Откат: удалить пакет и подкоманду; каталог снимков можно удалить вручную, он
не влияет на остальное состояние профиля.

## Open Questions

- Нужен ли автоматический снимок перед командами бэкенда? — Пока нет: дорого и
  непредсказуемо по объёму; вернёмся, если появится реальный сценарий.
- Нужна ли инкрементальная дельта между снимками? — Пока нет: простота важнее
  экономии места при текущих потолках.
