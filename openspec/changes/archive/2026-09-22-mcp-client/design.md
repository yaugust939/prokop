## Context

`prokop` выступает MCP-сервером для opencode (`prokop_mcp.py` вне
репозитория), но MCP-**клиента** в ядре нет. Единственный клиентский код —
`computer/cua.py`: он запускает демон `cua-driver` по stdio, пишет
JSON-RPC 2.0 запросы строками, читает ответ построчно, склеивает текстовые
блоки `tools/call`. Это ровно тот протокол, который нужен общему клиенту.

Следствия отсутствия общего клиента:
- ядро не расширяется извне — новая возможность требует правки кода;
- протокол продублирован под одну задачу и продублируется ещё раз при
  подключении второго сервера;
- гэп P1 в `docs/PARITY.md`.

Ограничения:
- проект держит минимум зависимостей (`httpx`, `PyYAML`); MCP SDK тянуть не
  хочется;
- клиент должен работать на Windows, macOS и Linux (запуск процесса —
  кроссплатформенный, кодировка — UTF-8, см. `backends`/`orchestrator`);
- тесты не должны запускать внешние процессы произвольно и не должны ходить
  в сеть — нужен управляемый локальный MCP-сервер-заглушка;
- инструменты внешнего сервера — это доступ к внешним данным, поэтому по
  умолчанию ничего не подключено.

## Goals / Non-Goals

**Goals:**
- Общий клиент MCP через stdio: запуск, рукопожатие, `tools/list`,
  `tools/call`, таймауты, закрытие.
- Инструменты внешних серверов попадают в `ToolRegistry` и вызываются
  обычным диспетчером ядра (как любые другие инструменты).
- Конфигурация серверов — в профиле (`mcp.servers`), выключено по умолчанию.
- Наблюдаемость и ручная проверка — подкоманда `prokop mcp`.
- Тесты полностью локальные: MCP-сервер-заглушка на stdlib.

**Non-Goals:**
- Транспорты кроме stdio (SSE/HTTP) — отдельная задача.
- Ресурсы и промпты MCP (`resources/*`, `prompts/*`) — только инструменты.
- OAuth/авторизация MCP-серверов.
- Перевод `computer/cua.py` на общий клиент — отдельная задача (не
  дестабилизируем GUI-автоматизацию).
- Автозапуск серверов на старте ядра и ленивое переподключение по health-check.

## Decisions

### D1: Свой JSON-RPC на stdlib, без MCP SDK
`asyncio` + `subprocess` + `json`, разделение сообщений по строкам
(newline-delimited JSON), как в `computer/cua.py`.

- *Рационально*: нулевая стоимость установки, единый стиль с уже
  существующим клиентом, полный контроль над таймаутами и завершением.
- *Альтернатива* (`mcp` SDK): новая зависимость ради того, что занимает
  ~150 строк, плюс расхождение с уже написанным кодом.

### D2: Клиент владеет процессом; жизненным циклом управляет рантайм
`McpClient` запускает процесс, держит stdin/stdout и закрывает процесс в
`close()`. Живыми клиентами владеет `McpRuntime` — один экземпляр на набор
включённых серверов.

- *Рационально*: спавн на каждый вызов даёт лишние сотни миллисекунд и теряет
  состояние сервера; вечный демон без владельца — утечка процессов.
- *Альтернатива* (спавн на вызов): просто, но медленно и без состояния.

### D3: Блокирующее чтение — в отдельном потоке с таймаутом и убийством процесса
`readline()` блокирующий; он выполняется в `asyncio.to_thread` под
`asyncio.wait_for`. При таймауте процесс завершается (тогда поток чтения
разблокируется), наружу летит ошибка с именем сервера и методом.

- *Рационально*: `wait_for` не может отменить поток, но завершение процесса
  снимает блокировку и не оставляет висящих потоков.
- *Альтернатива* (неблокирующие pipes/селекторы): на Windows не работает
  единообразно для pipe-дескрипторов.

### D4: Пространство имён и санитайзинг имён
Имя инструмента в реестре — `mcp__<сервер>__<инструмент>`, где недопустимые
символы (всё кроме `[A-Za-z0-9_-]`) заменяются на `_`. Обратная карта
хранится рядом, поэтому вызов уходит серверу под исходным именем.

- *Рационально*: имя функции модели обязано быть валидным идентификатором, а
  MCP допускает точки, слэши и юникод; санитайзинг без обратной карты потерял
  бы адрес.
- *Альтернатива* (отбрасывать «неудобные» инструменты): молча теряет
  возможности сервера.

### D5: Инструменты регистрируются только у доступных серверов
`McpRuntime.start()` поднимает включённые серверы; при неудаче сервер
пропускается с предупреждением, его инструменты не регистрируются. Серверы
по умолчанию выключены (`enabled: false`), если не указано иное.

- *Рационально*: недоступный сервер не должен ломать ядро и не должен
  расширять поверхность доступа без явного согласия пользователя.
- *Альтернатива* (регистрировать с `check_fn`, который спавнит процесс):
  `check_fn` синхронный и вызывается часто — спавн в нём недопустим.

### D6: Конфигурация — сырая секция в `Config`, разбор — в пакете `mcp`
`Config.mcp` хранит сырой словарь из YAML; типизированный разбор
(`McpServerConfig`) живёт в `prokop/mcp/config.py`.

- *Рационально*: `config.py` не тянет зависимости на пакет `mcp` (нет
  циклического импорта), а формат секции описывается в одном месте.
- *Альтернатива* (типы в `config.py`): циклический импорт либо дублирование
  моделей.

### D7: Тестовый MCP-сервер — скрипт на stdlib
В тестах используется маленький скрипт-заглушка (python-файл), который
отвечает на `initialize`, `tools/list`, `tools/call` по строкам. Он же
проверяет таймаут (по флагу «молчать»).

- *Рационально*: тесты воспроизводят реальный протокол, но полностью
  локальны, детерминированы и не зависят от внешних пакетов.

## Risks / Trade-offs

- [Сервер не отвечает / падает] → таймаут с завершением процесса и
  понятная ошибка; недоступный сервер пропускается при старте рантайма.
- [Утечка процессов] → `McpRuntime.aclose()` закрывает всех клиентов;
  клиент закрывает процесс при таймауте и в `__del__`-подобном `close()`.
- [Внешний сервер даёт доступ к данным] → серверы по умолчанию выключены;
  включение — явное действие в конфигурации профиля; включённые серверы
  видны в `prokop mcp list`.
- [Имена инструментов конфликтуют с ядром] → обязательный префикс `mcp__`;
  тенящая регистрация отклоняется реестром.
- [Смешение кодировок в stdio] → UTF-8 с заменой (как в `backends` и
  `orchestrator`).
- [Зависание при большом ответе] → построчное чтение с таймаутом на запрос;
  лимит размера результата — на стороне `Tool.result_limit`.

## Migration Plan

1. Добавить пакет `mcp` (клиент, конфиг, рантайм) — существующее поведение не
   меняется: без секции `mcp.servers` в профиле ничего не запускается.
2. Добавить набор `mcp` и подкоманду CLI.
3. Обновить документацию и `docs/PARITY.md`.
4. Прогнать тесты в матрице ubuntu/windows/macos.

Откат: удалить пакет `mcp` и подкоманду CLI; `Config.mcp` остаётся
необязательным полем и ни на что не влияет.

## Open Questions

- Нужны ли ресурсы/промпты MCP (`resources/*`, `prompts/*`)? — Пока нет:
  спроса не было, а инструменты закрывают основной сценарий.
- Нужен ли HTTP/SSE-транспорт для удалённых серверов? — Отдельная задача.
- Переводить ли `computer/cua.py` на общий клиент? — Да, но отдельным
  изменением, чтобы GUI-автоматизация не зависела от этой работы.
