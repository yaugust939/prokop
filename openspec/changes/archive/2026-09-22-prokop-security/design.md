## Context

Существующее состояние:

- `tools/safety.py` — рабочая классификация: жёсткий блок-лист (никогда),
  пользовательский deny-лист по глоб-паттернам, детектор опасных команд
  (нужно одобрение), иначе разрешено. Плюс метка опасности для показа.
- `tools/dispatcher.py` — вызывает `classify_command(args["command"])`
  **без** deny-паттернов и без записи решений.
- Конфигурация профиля (`prokop/config.py`) секции безопасности не имеет.
- Аудита нет: восстановить историю решений невозможно.

Ограничения:
- платформенная нейтральность — никаких Job Objects / namespaces / sandbox-exec;
- минимум зависимостей;
- решение должно быть проверяемым (тесты без побочных эффектов);
- сбой журнала не должен ломать выполнение инструмента;
- жёсткий блок-лист не должен обходиться настройками.

## Goals / Non-Goals

**Goals:**
- Единая точка решения по командам и путям: `allow` / `ask` / `deny`.
- Правила задаются в конфигурации профиля; приоритет правил предсказуем.
- Разрешающий список: пользователь может явно разрешить то, что детектор
  считает опасным.
- Аудит: каждое решение фиксируется, хвост журнала читается.
- Инспекция из терминала: показать действующие правила, проверить конкретную
  команду, посмотреть журнал.

**Non-Goals:**
- Изоляция процессов, файловой системы и сети (песочница) — отдельная,
  платформенно-специфичная задача.
- Ограничение прав уже запущенного процесса и его потомков.
- Управление секретами, шифрование журнала, ролевая модель.
- Переопределение жёсткого блок-листа настройками.
- Сетевые политики и прокси.

## Decisions

### D1: Слой политик поверх существующего классификатора
`prokop/security/policy.py` использует `tools/safety.classify_command` как
источник базовой оценки, а не дублирует детектор.

- *Рационально*: детектор уже специфицирован и покрыт; политика добавляет
  конфигурацию, разрешающий список и путь до решения, не переписывая детекцию.
- *Альтернатива* (свой детектор): дублирование и расхождение правил.

### D2: Приоритет правил фиксирован
Порядок: жёсткий блок-лист (deny, непереопределяемо) → `commands.deny`
(deny) → `commands.allow` (allow) → детектор опасных (ask) → allow.

- *Рационально*: deny всегда сильнее allow — «запретить на всякий случай»
  надёжнее, чем «разрешить»; явное разрешение снимает лишние подтверждения
  для доверенных команд; катастрофическое не обходится настройками.
- *Альтернатива* (allow сильнее deny): ошибка в allow-паттерне открывает
  дыру молча.

### D3: Политика путей — только для операций самого ядра
`check_path(path, mode)` применяется там, где ядро само пишет или читает:
инструмент `checkpoint` и команда `checkpoints restore`. Политика
**не** распространяется на команды терминала: содержимое shell-команды
статически не анализируется.

- *Рационально*: честно и предсказуемо; имитация контроля над произвольной
  командой была бы ложной гарантией (её и так покрывает D2 через детектор).
- *Альтернатива* (анализировать пути внутри команд): ненадёжный парсинг shell
  и ложное чувство защиты.

### D4: Пути по умолчанию разрешены, deny — защита
Для путей нет режима «спросить»: `paths.deny` даёт `deny`, `paths.allow`
перекрывает deny только при явном совпадении, иначе `allow`.

- *Рационально*: откат из снимка — массовая операция; подтверждение на каждый
  файл сделало бы её непригодной. Защита строится на запретах.
- *Альтернатива* (ask по умолчанию): непригодно на практике.

### D5: Аудит — JSONL, только добавление, best-effort
Запись в `<профиль>/logs/security.jsonl` через `prokop.paths`; ошибка записи
логируется и не прерывает действие; чтение — по хвосту с лимитом.

- *Рационально*: журнал не должен влиять на выполнение и не должен требовать
  СУБД; хвост закрывает реальный сценарий «что было недавно».
- *Альтернатива* (SQLite): лишняя зависимость от состояния БД и блокировок.

### D6: Политика читается из конфигурации лениво и кэшируется
`get_policy()` строит политику из конфигурации профиля при первом обращении;
`reset_policy()` сбрасывает кэш (для тестов и смены конфигурации).

- *Рационально*: диспетчер инструментов не должен читать YAML на каждый вызов;
  шаблон совпадает с `get_registry()`/`reset_registry()` в ядре.
- *Альтернатива* (передавать политику в каждый вызов): протаскивание
  зависимости через весь стек вызовов инструментов.

### D7: Границы зафиксированы в выводе и документации
`prokop security show` печатает не только правила, но и явное указание, что
слой не изолирует процессы.

- *Рационально*: главный риск такого слоя — ложное чувство защищённости;
  границу нужно показывать там, где пользователь её читает.

## Risks / Trade-offs

- [Ложное чувство защищённости] → D7: границы в выводе и документации;
  формулировка «политики, не песочница» в README и GUIDE.
- [Ошибка в allow-паттерне открывает дыру] → D2: deny приоритетнее, жёсткий
  блок-лист непереопределяем; `security check` показывает решение по конкретной
  команде до её выполнения.
- [Журнал растёт] → запись только строк, чтение по хвосту; ротация — вне скоупа
  и отмечена как известное ограничение.
- [Политика читается один раз и устаревает] → `reset_policy()` и пересоздание
  политики на каждое чтение в CLI; для диспетчера кэш сознателен.
- [Сбой записи журнала] → best-effort: ошибка логируется, действие не падает.
- [Пути с кириллицей и разными разделителями] → сравнение нормализует путь
  (прямые слэши, регистронезависимо на Windows) и проверяет и исходную, и
  разрешённую форму.

## Migration Plan

1. Добавить пакет `security` — при отсутствии секции `security` поведение
   совпадает с текущим (детектор + жёсткий блок-лист).
2. Перевести диспетчер на политику: deny из конфигурации, allow, аудит.
3. Добавить проверку путей в инструменте и CLI снимков.
4. Добавить подкоманду `security`, обновить документацию и `docs/PARITY.md`.
5. Прогнать тесты в матрице ubuntu/windows/macos.

Откат: удалить пакет и подкоманду, вернуть в диспетчере прямой вызов
`classify_command` — остальное поведение не затронуто.

## Open Questions

- Нужна ли ротация журнала? — Пока нет: чтение по хвосту закрывает сценарий,
  объём растёт медленно; вернёмся при реальной эксплуатации.
- Нужен ли режим «спросить» для путей? — Пока нет: делает массовый откат
  непригодным (D4).
- Нужна ли интеграция с сетевыми политиками? — Вне скоупа.
