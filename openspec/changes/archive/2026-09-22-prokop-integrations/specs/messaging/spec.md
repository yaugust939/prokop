## ADDED Requirements

### Requirement: Адаптер платформы Telegram

Ядро SHALL предоставлять реализацию контракта адаптера платформы для Telegram
поверх HTTP Bot API, без новых внешних зависимостей. Адаптер SHALL
реализовывать обязательные операции контракта: подключение с проверкой
учётных данных, отключение, отправку текста, индикатор набора и информацию о
чате, а также отправку медиа-вложения.

#### Scenario: Подключение с корректными учётными данными

- **WHEN** адаптер подключается и платформа подтверждает учётные данные
- **THEN** подключение считается установленным

#### Scenario: Подключение с неверными учётными данными

- **WHEN** платформа отвечает отказом авторизации
- **THEN** поднимается ошибка подключения с понятным текстом

#### Scenario: Отправка текста

- **WHEN** текст отправлен в чат и платформа приняла сообщение
- **THEN** результат успешен и содержит идентификатор сообщения

#### Scenario: Индикатор набора

- **WHEN** запрошен индикатор набора
- **THEN** платформе отправляется соответствующее действие

#### Scenario: Информация о чате

- **WHEN** запрошена информация о чате
- **THEN** возвращаются идентификатор, заголовок и вид чата

#### Scenario: Отправка медиа

- **WHEN** запрошена отправка файла в чат
- **THEN** файл отправляется платформе, результат содержит признак успеха

### Requirement: Отображение ошибок платформы в категории контракта

Адаптер SHALL отображать ответы и сбои платформы в категории ошибок контракта:
отказ авторизации — авторизация, ограничение частоты — лимит частоты, сбои
сервера — временная ошибка, сетевые сбои — сеть, неверный запрос — неверные
данные, прочее — неизвестная ошибка. Отправка MUST NOT поднимать исключение
наружу: сбой возвращается результатом с категорией.

#### Scenario: Ограничение частоты

- **WHEN** платформа отвечает ограничением частоты
- **THEN** результат содержит категорию «лимит частоты» и признак
  повторяемости

#### Scenario: Сбой сервера платформы

- **WHEN** платформа отвечает ошибкой сервера
- **THEN** результат содержит временную категорию и признак повторяемости

#### Scenario: Сетевой сбой

- **WHEN** запрос к платформе не доходит из-за сетевой ошибки
- **THEN** результат содержит сетевую категорию, исключение не поднимается

#### Scenario: Отказ авторизации при отправке

- **WHEN** платформа отвечает отказом авторизации на отправку
- **THEN** результат содержит категорию авторизации без признака повторяемости

### Requirement: Разбиение длинных сообщений

Адаптер SHALL разбивать текст, превышающий лимит платформы, на части и
отправлять их последовательно. Разбиение SHALL по возможности происходить по
границе строки, а не по середине слова. При неудаче отправки части MUST
возвращаться результат этой неудачи.

#### Scenario: Длинный текст

- **WHEN** длина текста превышает лимит платформы
- **THEN** текст отправляется несколькими сообщениями, каждое не длиннее лимита

#### Scenario: Неудача на одной из частей

- **WHEN** отправка одной из частей завершилась ошибкой
- **THEN** результат содержит категорию этой ошибки

#### Scenario: Короткий текст

- **WHEN** длина текста не превышает лимит
- **THEN** отправляется одно сообщение

### Requirement: Нормализация входящих сообщений

Адаптер SHALL приводить сырое обновление платформы к нормализованному событию
гейтвея: текст, тип сообщения, автор, источник (платформа, вид чата, чат,
тред), вложения и контекст ответа. Обновления без сообщения MUST
игнорироваться. Адаптер SHALL предоставлять длинный опрос обновлений с
позицией для продолжения.

#### Scenario: Текстовое сообщение

- **WHEN** получено обновление с текстовым сообщением
- **THEN** событие содержит текст, автора и источник с идентификатором чата

#### Scenario: Медиа-сообщение

- **WHEN** получено обновление с фотографией или документом
- **THEN** тип события соответствует вложению, а вложения перечислены

#### Scenario: Ответ на сообщение

- **WHEN** сообщение является ответом на другое сообщение
- **THEN** в событии указан контекст ответа

#### Scenario: Обновление без сообщения

- **WHEN** обновление не содержит сообщения
- **THEN** нормализация возвращает отсутствие события

#### Scenario: Тематический тред

- **WHEN** сообщение принадлежит треду (теме)
- **THEN** идентификатор треда попадает в источник события

#### Scenario: Длинный опрос

- **WHEN** запрошены обновления с позицией продолжения
- **THEN** платформе передаётся позиция и запрашиваемое время ожидания
