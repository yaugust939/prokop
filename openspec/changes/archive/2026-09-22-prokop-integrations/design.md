## Context

Существующее состояние:

- `memory/provider.py` — контракт `MemoryProvider` (init, prefetch,
  sync_turn, инструменты, хуки) и встроенный провайдер с фактами в памяти
  процесса (теряются при выходе).
- `memory/manager.py` — оркестрация: встроенный всегда первый, максимум один
  внешний, фан-аут с устойчивостью к сбоям, сериализованный воркер записей.
- **Разрыв**: `MemoryManager.set_external` не вызывается ни из одного места,
  то есть `memory.provider` из конфигурации профиля не влияет ни на что.
- `gateway/adapters.py` — контракт `PlatformAdapter` (connect, disconnect,
  send_text с категорией ошибки, set_typing, chat_info, опциональные медиа).
- `gateway/events.py` — `InboundEvent` (текст, автор, источник, тип, вложения,
  контекст ответа) — во что адаптер обязан приводить сырое сообщение.
- `gateway/engine.py` — `Gateway.handle(event)`: авторизация → защита от
  параллельных ходов → ход → подготовка ответа. Платформенный ввод-вывод
  остаётся на адаптере.
- **Реализаций нет ни одной**: ни провайдера памяти, ни адаптера платформы.

Ограничения:
- зависимости не добавляются (`httpx` уже используется транспортом);
- платформенная нейтральность (файлы, HTTP — одинаково на всех ОС);
- тесты не должны ходить в сеть: HTTP подменяется транспортом `httpx`;
- секреты не попадают в проект (хранилище памяти — в домашнем каталоге профиля);
- контракты не меняются — меняется только их наполнение.

## Goals / Non-Goals

**Goals:**
- Подключить `memory.provider` из конфигурации: имя → реализация.
- Дать память, которая переживает перезапуск и приносит релевантный контекст.
- Дать рабочий адаптер платформы, доказывающий пригодность контракта.
- Тесты обеих реализаций полностью локальные.

**Non-Goals:**
- Полный набор платформ (одна платформа как доказательство контракта).
- Векторный поиск и эмбеддинги (только ключевые слова, без зависимостей).
- Автоматическое извлечение фактов моделью (факты пишет агент инструментом).
- Запуск гейтвея как сервиса (демон, автозапуск) — вне скоупа.
- Вебхуки Telegram (используется длинный опрос).
- Управление секретами и шифрование памяти.

## Decisions

### D1: Фабрика как единственная точка разрешения провайдера
`memory/factory.py`: `build_provider(config, home)` возвращает внешний
провайдер или `None`; `build_manager(config, home)` собирает `MemoryManager` с
подключённым внешним провайдером.

- *Рационально*: закрывает реальный разрыв (конфигурация ни на что не влияла);
  одна точка, где имя превращается в объект.
- *Альтернатива* (регистрация через точки входа пакета): для одного-двух
  провайдеров избыточно; добавим, если появится экосистема.

### D2: Неизвестный провайдер — предупреждение, а не падение
Имя, которого нет в реестре провайдеров, даёт предупреждение в лог и
встроенную память.

- *Рационально*: опечатка в конфигурации не должна ломать запуск агента;
  встроенная память — безопасное поведение по умолчанию.
- *Альтернатива* (ошибка): ломает запуск из-за опечатки.

### D3: Хранилище памяти — JSONL в профиле, только добавление
`<профиль>/memory/memory.jsonl`: одна запись на строку (`fact` или `turn`),
чтение — с последней к первой, факты дедуплицируются по ключу (побеждает
последний).

- *Рационально*: дописывание дёшево и безопасно при сбое; частично
  повреждённый файл не делает память нечитаемой (битые строки пропускаются);
  формат читаем глазами и совместим с `prokop memory`.
- *Альтернатива* (SQLite): состояние БД и блокировки там, где достаточно
  строк; поиск по ключевым словам всё равно делается в памяти.

### D4: Релевантность — пересечение токенов, без зависимостей
`prefetch(query)` оценивает записи по пересечению токенов запроса и текста
(регистронезависимо, поддержка кириллицы), возвращает верхние N фактов и
дайджестов ходов; пустой запрос даёт самые свежие факты.

- *Рационально*: предсказуемо, объяснимо, тестируемо, ноль зависимостей;
  для памяти агента этого достаточно.
- *Альтернатива* (эмбеддинги): новая зависимость и недетерминизм в тестах.

### D5: Ограничение объёма — компактизация при перезаписи
При превышении лимита записей файл переписывается с сохранением самых свежих
(атомарно: временный файл + переименование).

- *Рационально*: память не растёт бесконечно; операция редкая и локальная.
- *Альтернатива* (без лимита): рост файла и времени чтения.

### D6: Telegram — HTTP-вызовы Bot API через `httpx`
Один клиент на адаптер, методы вызываются по имени (`getMe`, `sendMessage`,
`sendChatAction`, `getChat`, `getUpdates`, `sendDocument`), ошибки
отображаются в категории контракта: 401/403 → `AUTH`, 429 → `RATE_LIMIT`,
5xx → `TRANSIENT`, сетевые сбои → `NETWORK`, 400 → `INVALID`.

- *Рационально*: `httpx` уже зависимость; отображение в категории делает
  поведение ретраев осмысленным (контракт уже описывает `is_retryable`).
- *Альтернатива* (библиотека-обёртка платформы): новая зависимость ради
  четырёх методов.

### D7: Входящие — длинный опрос и явная нормализация
Адаптер отдаёт `get_updates(offset, timeout)` и `normalize(update)` →
`InboundEvent`. Цикл опроса не входит в ядро: его собирает вызывающий код
(как `run_turn` в гейтвее).

- *Рационально*: адаптер остаётся тонким и тестируемым (нормализация — чистая
  функция над словарём обновления); политика запуска — решение потребителя.
- *Альтернатива* (вебхуки): нужен публичный адрес и сервер — вне скоупа.

### D8: Разбиение длинных сообщений по лимиту платформы
`send_text` режет текст на части по `max_text_length` (4096), по возможности
по границе строки, и отправляет их последовательно; результат — по первой
неудаче.

- *Рационально*: длинные ответы агента — обычное дело, а платформа жёстко
  ограничивает длину сообщения.

## Risks / Trade-offs

- [Сетевые сбои платформы] → D6: категории ошибок и `retryable` по контракту;
  адаптер не бросает исключения на уровне `send_text`.
- [Рост хранилища памяти] → D5: лимит записей и компактизация.
- [Секреты попадают в память] → хранилище в профиле, а не в проекте;
  предупреждение в документации.
- [Повреждённый файл памяти] → битые строки пропускаются, память продолжает
  работать; полный сбой чтения даёт пустую память, а не падение агента.
- [Тесты сетевого адаптера могут «протечь» в сеть] → используется
  `httpx.MockTransport`; реальных запросов нет.
- [Расхождение контракта и реализации со временем] → тесты покрывают каждую
  обязательную операцию контракта.

## Migration Plan

1. Добавить фабрику и файловый провайдер — без секции `memory.provider`
   поведение прежнее (только встроенная память).
2. Добавить адаптер Telegram — ничего не запускается, пока его не создадут.
3. Добавить подкоманду `memory`, обновить документацию и `docs/PARITY.md`.
4. Прогнать тесты в матрице ubuntu/windows/macos.

Откат: удалить новые модули и подкоманду; контракты не менялись.

## Open Questions

- Нужен ли второй адаптер (например, файловый/вебхук) для полноты картины? —
  Пока нет: один адаптер доказывает контракт; следующий — по запросу.
- Нужна ли запись памяти из `sync_turn` автоматически (дайджесты)? — Да,
  реализуется в D3/D4: дайджест хода — обычная запись, доступная поиску.
- Нужна ли ротация журнала опроса? — Вне скоупа: состояние опроса (offset)
  держит вызывающий код.
