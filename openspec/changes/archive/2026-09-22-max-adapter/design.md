## Context

Контракт адаптера платформы (`gateway/adapters.py`) и нормализованное событие
(`gateway/events.py`) уже специфицированы; реализован Telegram
(`gateway/telegram.py`). Адаптера MAX нет.

**Что удалось установить по официальной документации** (`dev.max.ru/docs-api`,
OpenAPI-схема `github.com/max-messenger/api-schema`):

| Аспект | MAX |
|---|---|
| База | `https://platform-api2.max.ru` (не `platform-api.max.ru`) |
| Авторизация | заголовок `Authorization: <access_token>` (query-параметр больше не поддерживается) |
| Лимиты | 30 rps на API; не более 2 сообщений в секунду в один чат |
| Текст сообщения | до 4000 символов |
| Идентификаторы | `chat_id`/`user_id` — int64; `mid` (идентификатор сообщения) — **строка** |
| Отправка | `POST /messages?chat_id=<int>` или `?user_id=<int>`, тело `{text, attachments, link, notify, format}` |
| Ответ на сообщение | `link: {type: "reply", mid: "<строка>"}` |
| Индикатор набора | `POST /chats/{chatId}/actions` `{"action": "typing_on"}` — **только групповые чаты** |
| Информация о чате | `GET /chats/{chatId}` → `{chat_id, type: dialog\|chat\|channel, title, participants_count, ...}` |
| Обновления | `GET /updates?limit&timeout&marker&types` → `{"updates": [...], "marker": <int\|null>}` |
| Загрузка медиа | `POST /uploads?type=image\|video\|audio\|file` → `{url, token?}`; затем загрузка по `url` (multipart, поле `data`) |
| Ошибки | коды 400/401/404/405/429/503, тело `{"code": ..., "message": ...}` |

**События.** Базовый `Update`: `{update_type, timestamp (мс), chat_id, user, is_channel}`.
- `message_created` → `message` (обязательное) + `user_locale`;
- `message_callback` → `callback {timestamp, callback_id, payload?, user}` + `message` (может быть `null`).

**Message**: `{sender?: User, recipient: {chat_id?, chat_type, user_id?}, timestamp (мс), link?: {type, sender?, chat_id, message}, body?: {mid, seq, text?, attachments?}, url?}`.
Отправитель отсутствует у постов канала.

Ограничения: живого токена бота нет, поэтому проверка — на подменённом
транспорте `httpx`; сертификат Минцифры в список доверенных не входит в скоуп
(это задача окружения, а не адаптера).

## Goals / Non-Goals

**Goals:**
- Второй полноценный адаптер платформы, подтверждающий переносимость контракта.
- Покрытие всех обязательных операций контракта и обеих операций с медиа.
- Полностью локальные тесты (подменённый транспорт, реальных запросов нет).

**Non-Goals:**
- Webhook-подписки (`POST /subscriptions`) — адаптер использует длинный опрос,
  как Telegram-адаптер; вебхуки требуют публичного HTTPS-адреса.
- Кнопки и callback-ответы (`inline_keyboard`, `POST /answers`) — приходят как
  события, но отправка клавиатур не входит в контракт.
- Каналы как объект управления (закрепление, комментарии, администраторы).
- Мини-приложения MAX Bridge.
- Ротация и хранение токена (передаётся вызывающим кодом).

## Decisions

### D1: Отдельный модуль, общий контракт, ноль новых зависимостей
`gateway/max.py` реализует `PlatformAdapter`; HTTP — через `httpx`, клиент
инжектируется для тестов.

- *Рационально*: как у Telegram; тесты не выходят в сеть.
- *Альтернатива* (общая абстракция «Telegram-подобный API»): MAX отличается по
  существу — указатель `marker`, строковый `mid`, адресация диалога, индикатор
  набора только в группах; общий слой скрыл бы различия и сломал бы один из
  адаптеров при изменении другого.

### D2: Адресация получателя: `chat_id` по умолчанию, `user:<id>` для диалога
Контракт передаёт только `chat_id`. MAX различает `chat_id` (чат/канал) и
`user_id` (пользователь). Правило: значение вида `user:<id>` уходит как
`user_id`, любое другое — как `chat_id`.

- *Рационально*: идентификатор из события используется как есть (документация
  прямо говорит, что `chat_id` приходит в `Update`); диалог адресуется явным,
  видимым в логах способом, без скрытой эвристики.
- *Альтернатива* (определять по сохранённому типу чата): требует состояния и
  ломается после перезапуска; к тому же тип чата не всегда известен.

### D3: Указатель длинного опроса хранится в адаптере
`get_updates()` возвращает список обновлений и обновляет `self.marker`;
вызывающий код может прочитать и сохранить его.

- *Рационально*: `marker` — непрозрачный указатель, и его владелец — тот, кто
  опрашивает; сигнатура совпадает с Telegram-адаптером (список обновлений),
  поэтому цикл обработки платформо-независим.
- *Альтернатива* (возвращать пару значений): ломает единообразие адаптеров.

### D4: Индикатор набора — best-effort и только для групп
Для диалогов действие не отправляется (платформа его не поддерживает), ошибка
не поднимается наружу.

- *Рационально*: контракт возвращает `None`; вызывающий код не должен падать
  из-за косметики.
- *Альтернатива* (всегда вызывать): лишние ошибки 400/404 на каждый ход.

### D5: Медиа — двухшаговая загрузка с типом по расширению
Тип вложения определяется расширением файла (`image`/`video`/`audio`/`file`),
затем `POST /uploads?type=...` → загрузка по выданному `url` (multipart, поле
`data`) → токен вложения → `POST /messages` с `attachments`.

- *Рационально*: так работает платформа; токен ищется и в ответе на первый
  запрос, и в ответе на загрузку (для разных типов он приходит в разных
  местах), поэтому реализация устойчива к обоим вариантам.
- *Альтернатива* (отправка по `url`): доступна только для изображений и менее
  надёжна (внешний источник может исчезнуть).

### D6: Нормализация двух типов событий
`message_created` → текстовое событие (текст из `body.text`, автор из
`sender`/`user`, вложения по типам), `message_callback` → нажатие кнопки
приходит как текст с payload. Остальные типы игнорируются.

- *Рационально*: покрывает реальные сценарии диалога; прочие события
  (`bot_added`, `chat_title_changed`, ...) не являются сообщениями.
- *Альтернатива* (только `message_created`): нажатия кнопок терялись бы.

### D7: Категории ошибок по документированным кодам
401 → авторизация, 429 → лимит частоты, 5xx (включая 503) → временная,
400/404/405 → неверные данные, сетевые сбои → сеть. `send_text` не поднимает
исключений; `connect` поднимает `SendError`.

- *Рационально*: соответствует контракту и делает `is_retryable` осмысленным.

## Risks / Trade-offs

- [Живого бота нет] → тесты на `httpx.MockTransport`; факты о API зафиксированы
  в этом документе со ссылкой на официальную документацию и OpenAPI-схему.
- [Адресация диалога] → D2: явный префикс `user:` и документирование; ошибка
  отправки видна сразу и не маскируется.
- [Различие поведения API и документации] → все поля читаются защищённо
  (отсутствие поля не роняет нормализацию), ошибки возвращаются категорией.
- [Загрузка медиа может быть не готова сразу] → платформа отдаёт
  `attachment.not.ready`; категория ошибки позволит вызывающему коду повторить.
- [Сертификат Минцифры] → вне скоупа адаптера; отмечено в документации.

## Migration Plan

1. Добавить модуль `max.py` — ничего не запускается, пока адаптер не создан.
2. Покрыть тестами, обновить документацию и `docs/PARITY.md`.
3. Прогнать тесты в матрице ubuntu/windows/macos.

Откат: удалить модуль; контракт не менялся.
