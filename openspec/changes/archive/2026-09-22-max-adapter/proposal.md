## Why

MAX — российский мессенджер, для которого у ядра нет адаптера, хотя контракт
`PlatformAdapter` уже реализован на Telegram и проверен. Для проекта,
работающего в РФ, MAX важнее остальных платформ: именно там находятся
пользователи и организации. Нужен второй адаптер, подтверждающий, что контракт
не «подогнан» под одну платформу, и дающий рабочий канал общения с агентом.

## What Changes

- Новый модуль `src/prokop/gateway/max.py` — реализация контракта
  `PlatformAdapter` поверх Bot API MAX (`platform-api2.max.ru`) через `httpx`,
  без новых зависимостей:
  - подключение с проверкой токена (`GET /me`), отключение;
  - отправка текста с разбиением по лимиту платформы (4000 символов) и
    контекстом ответа (`link: {type: reply, mid}`);
  - индикатор набора (`POST /chats/{chatId}/actions`) с учётом того, что
    действие доступно только в групповых чатах;
  - информация о чате (`GET /chats/{chatId}`);
  - отправка файлов через двухшаговую загрузку (`POST /uploads` → загрузка по
    выданной ссылке → вложение в сообщении);
  - длинный опрос (`GET /updates`) с указателем `marker`;
  - нормализация входящих событий (`message_created`, `message_callback`) в
    `InboundEvent`;
  - отображение ошибок платформы в категории контракта.
- Адресация получателя: по умолчанию `chat_id` (как документировано для
  идентификатора из события), с явным префиксом `user:<id>` для диалога —
  MAX различает отправку в чат/канал и пользователю.

## Impact

- Новые файлы: `src/prokop/gateway/max.py`, `src/tests/test_max_adapter.py`.
- Документация: `README.md`, `docs/GUIDE.md`, `docs/PARITY.md`, `CHANGELOG.md`.
- Зависимости не добавляются (`httpx` уже используется).
- Риски: различия Bot API MAX и Telegram (указатель `marker` вместо смещения,
  строка в идентификаторе сообщения, адресация диалога через `user_id`,
  индикатор набора только в групповых чатах) — все они зафиксированы в
  требованиях и тестах; недоступность живого бота компенсируется тестами на
  подменённом транспорте.
