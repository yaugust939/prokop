## ADDED Requirements

### Requirement: Обработка хода

Система SHALL обрабатывать один пользовательский ход как замкнутый цикл: пролог → итеративный вызов модели с инструментами → финализация. Пролог MUST выполнять одноразовую настройку (санитизация ввода, восстановление/построение системного промпта, префлайт-компрессия, предзагрузка памяти), а финализация MUST сбрасывать счётчики, записывать транскрипт и запускать фоновые пост-обработчики.

#### Scenario: Ход без вызова инструментов
- **WHEN** модель возвращает текстовый ответ без запросов на вызов инструментов
- **THEN** ход завершается, ответ становится финальным, транскрипт сохраняется в хранилище

#### Scenario: Ход с вызовами инструментов
- **WHEN** модель возвращает вызовы инструментов
- **THEN** инструменты исполняются, результаты добавляются как сообщения роли `tool`, цикл продолжается до текстового ответа

### Requirement: Бюджеты итераций и времени

Система SHALL ограничивать число вызовов модели бюджетом итераций (общим для родителя и субагентов) и бюджетом настенных часов. При исчерпании итераций MUST допускаться один «грациозный» завершающий вызов. При пересечении порога времени MUST впрыскиваться одноразовая заметка о необходимости свернуть работу.

#### Scenario: Исчерпан бюджет итераций
- **WHEN** число вызовов модели достигает бюджета итераций
- **THEN** цикл выполняет максимум один завершающий вызов и финализирует ход из текущего состояния

#### Scenario: Порог настенных часов
- **WHEN** использовано более 80% бюджета настенных часов
- **THEN** в контекст впрыскивается одноразовая заметка о сворачивании, не нарушающая чередование ролей

### Requirement: Прерывание, steer и redirect

Система SHALL поддерживать три механизма коррекции активного хода: прерывание (мягкая/жёсткая остановка цикла из другого потока), steer (впрыск текста в результат последнего инструмента без остановки) и redirect (отмена текущего запроса модели с сохранением завершённых результатов инструментов и повтор хода с коррекцией как пользовательским сообщением).

#### Scenario: Мягкое прерывание
- **WHEN** приходит новое сообщение или нажат «стоп»
- **THEN** долгие инструменты получают сигнал завершиться раньше, сигнал распространяется на параллельные воркеры и субагентов

#### Scenario: Steer во время исполнения инструмента
- **WHEN** пользователь вводит steer-текст пока исполняется инструмент
- **THEN** текст впрыскивается в вывод инструмента следующей итерации, не прерывая текущий вызов

#### Scenario: Redirect после частичного ответа
- **WHEN** выполняется redirect активного хода
- **THEN** завершённые результаты инструментов сохраняются, частичный ответ понижается до текста, коррекция добавляется как пользовательское сообщение, ход повторяется

### Requirement: Стриминг и обработка рассуждений

Система SHALL стримить текстовые дельты ответа через колбэк и доставлять события жизненного цикла инструментов (старт/прогресс/завершение). Рассуждения (chain-of-thought) MUST обрабатываться как только-отображаемое состояние и NEVER сериализоваться обратно в контент сообщений.

#### Scenario: Стриминг дельт
- **WHEN** модель стримит ответ
- **THEN** текстовые дельты доставляются через колбэк стриминга по мере генерации

#### Scenario: Рассуждения не попадают в реплей
- **WHEN** модель возвращает chain-of-thought
- **THEN** рассуждения доступны для отображения, но не включаются в сохраняемый контент сообщений

### Requirement: Стабильность системного промпта

Система SHALL строить системный промпт один раз на сессию, кэшировать его и сохранять в хранилище, восстанавливая дословно на последующих ходах. Внешняя память/контекст провайдеров MUST впрыскиваться в пользовательское сообщение, а не в системный промпт.

#### Scenario: Повторное использование системного промпта
- **WHEN** начинается новый ход существующей сессии
- **THEN** системный промпт восстанавливается из хранилища байт-в-байт без перестройки

#### Scenario: Впрыск памяти не ломает префикс
- **WHEN** провайдер памяти возвращает контекст
- **THEN** контекст добавляется в пользовательское сообщение, системный промпт не изменяется

### Requirement: Обработка ошибок и ретраи

Система SHALL обрабатывать транзиентные ошибки API (rate-limit, перегрузка, таймауты) механизмом повторных попыток с адаптивной задержкой и классифицировать ошибки в структурированный результат с флагом retryable. Детерминированные локальные ошибки MUST NOT ретраиться.

#### Scenario: Транзиентная ошибка API
- **WHEN** провайдер возвращает rate-limit или таймаут
- **THEN** система повторяет вызов с адаптивной задержкой и в итоге возвращает структурированный результат

#### Scenario: Детерминированная локальная ошибка
- **WHEN** возникает локальная ошибка валидации ввода
- **THEN** система не ретраит и возвращает понятный финальный результат

### Requirement: Устойчивость сессии

Система SHALL брать устойчивую аренду (lease) на сессию перед ходом, чтобы несколько процессов не писали в один разговор, продлевать её фоновым потоком и освобождать по завершении.

#### Scenario: Конкуренция за сессию
- **WHEN** два процесса пытаются писать в одну сессию
- **THEN** только владелец аренды пишет, потеря аренды приводит к прерыванию хода
